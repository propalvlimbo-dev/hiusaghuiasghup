# План: капча + управление ботами + максимальный стресс-тест

Три требования из задачи закрываются **одним стеком**, но не одним инструментом:
капча и управление — это SoulFire, а потолок нагрузки добирается «заливными» ботами и
серверными фейк-игроками.

| Требование | Чем закрывается | Почему именно так |
|---|---|---|
| **1. Работа с капчей** | **SoulFire** (`captcha-solver`: MAP_IN_HAND / POV_RENDER / TEXT_BASED) + **bypass** для flood-слоя | Ни один flood-инструмент (rust-mc-bot, BotMark, mc-bots) капчу не умеет: бот не «видит» мир. Решать её может только полноценный клиент — это SoulFire |
| **2. Управление ботами** | **SoulFire**: GUI, CLI, консольные команды, визуальные скрипты, SDK, MCP | Единственный из инструментов с полноценной панелью управления флотом |
| **3. Максимально лучший стресс-тест** | **3 слоя**: SoulFire (поведение) + mc-bots/rust-mc-bot (потолок соединений) + Carpet/BetterStressbots (геймлогика) | «Лучший тест» = не одна цифра, а четыре разных теста: вход, поведение, спайк, выносливость |

**Главный принцип:** *капчу не решают за 500 ботов — её либо решают на нескольких ботах
(валидация «проходит ли живой бот защиту»), либо обходят на своём сервере для машины-генератора
нагрузки.* Это и есть инженерно правильное решение, см. §1.3.

## 1. Требование «работает с капчей»

### 1.1. Кто вообще способен пройти капчу

| Инструмент | Умеет капчу? | Почему |
|---|---|---|
| **SoulFire** | **Да** | Полный клиент + AI-плагин: видит карту в руке, «видит» POV-рендер, читает чат |
| mc-bots | Нет (только `-j` команда на входе) | Может отправить `/register`, но не распознать код |
| rust-mc-bot / BotMark | Нет | Бот почти не обрабатывает мир |
| LambdaAttack | Нет (только авто-`/register`) | Устаревший протокол, капчи нет в коде |
| Carpet / BetterStressbots | **Не нужна** | Боты создаются внутри сервера, минуя экран капчи |
| Mineflayer-скрипты | Только если писать самому | Можно собрать цепочку «увидеть карту → отправить в LLM», но это разработка |

Вывод: если капча должна **проходиться**, а не обходиться — берите SoulFire.

### 1.2. Настройка SoulFire `captcha-solver` под конкретный тип капчи

Плагин работает через общий **AI Settings** (Base URL, API Key, timeout, retries) и
умеет три режима. Выбор режима — по типу вашей капчи:

| Ваша капча | Режим SoulFire | Источник/триггер | Тонкости |
|---|---|---|---|
| **mapcha**, **Minecaptcha**, **CaptchaVerifyZ** (карта в руке/инвентаре) | `MAP_IN_HAND` | — | SoulFire читает карту именно из **главной руки**. У mapcha `inventory_slot` по умолчанию `4`; у Minecaptcha есть опция `map_in_offhand`. Убедитесь, что слот с картой выбран (или карта в главной руке), иначе изображение не считаеться |
| Капча нарисована в мире/на экране (голограмма, стена, титул) | `POV_RENDER` | — | Поднимите `POV Render Width/Height`, пока цифры не станут читаемыми; бесполезен без рабочего рендера (SoulFire тащит свой Vulkan-рантайм, дисплей не нужен) |
| **UltimateAntiBot** (`verification.method: CHAT`, 6 символов) и аналоги, где код приходит текстом | `TEXT_BASED` | **Captcha Regex** с группой захвата, по умолчанию `/captcha (\w+)` | Никакой модели не нужно — просто регулярка + Response Command |
| Капча появляется после сообщения в чате, а картинку надо ещё получить | `CHAT_MESSAGE` | **Text Trigger** | Комбо: чат-триггер → картинка |

Что обязательно проверить:

- **Model** — только **vision-модель**, если используете картинку. На Groq, например,
  `meta-llama/llama-4-scout-17b-16e-instruct`; локально (Ollama) по умолчанию заложена `llava`
  — капча не уходит в облако (важно, если не хотите отдавать чужие картинки наружу).
- **Response Command** — шаблон ответа, куда подставляется распознанное (по умолчанию
  подстановка `.formatted(text)`).
- **Prompt** — системная инструкция («извлеки код с картинки, ответь только кодом»).
- Ограничения из кода плагина: ответ обрезается до **32 символов**, лимит генерации 64 токена,
  перед отправкой текст чистится под чат. Для длинных кодов/фраз не подойдёт.
- Провайдер должен быть **доступен с машины SoulFire backend** (в Docker — с учётом сети контейнера).

**Безопасность:** solver нужен для тестирования **своей** защиты. На чужом сервере это уже
обход защиты, а не тест.

### 1.3. Как быть с капчей на масштабе (это ключевое место)

Решать капчу на каждом из 200 ботов бессмысленно: вы упрётесь в латентность и лимиты LLM
(плюс стоимость), а измерять будете не свой сервер, а свою же защиту. Правильная схема — **два
режима в двух разных окнах теста**:

**Окно A — «реалистичный бот» (капча ВКЛючена).**
SoulFire, 1–10 ботов, solver включён. Цель — доказать, что живой клиент проходит вашу капчу,
и увидеть, сколько времени/шагов это занимает у настоящего игрока. Это тест UX защиты,
а не нагрузки.

**Окно B — «нагрузка» (капча выключена для машины генератора).**
Внешние боты (SoulFire на 50+ / mc-bots / rust-mc-bot). Капчу им не пройти в принципе, поэтому
на тестовом инстансе делаем **bypass именно для генератора**, а не отключаем защиту целиком:

| Что у вас стоит | Как дать bypass тестовой машине | Что НЕ ломается |
|---|---|---|
| **EpicGuard** | `/guard whitelist add <адрес или ник>`; permission `epicguard.bypass`; либо `check-mode: ... NEVER` на тестовом инстансе | Остальные проверки остаются активными для обычных игроков |
| **mapcha** | permission **`mapcha.bypass`** (в профиле бота/аккаунта через LuckPerms), либо `cache: true` + один пройденный вход | Капча продолжает защищать реальных игроков |
| **Sonar / LimboFilter / BotSentry** | Белый список IP/прокси-подсети тестовой машины в конфиге, либо временно `ATTACK`-режим только для «своих» | — |
| **iptables/ipset** | Добавить IP генератора в разрешающий набор **до** `-j DROP` | Фильтрация остального трафика не меняется |
| **Строгий путь без поблажек** | Держать капчу включённой и гонять **только серверных ботов** (BetterStressbots/Carpet) | Сеть/авторизация не тестируются, зато геймлогика — честно |

**Окно C — «тест анти-бота» (капча ВКЛючена, боты её ломают).**
Отдельный прогон: flood-боты против включённой защиты. Вопрос — «ловит ли капча/анти-бот флуд и
как быстро включается attack-режим». Здесь смотрим блокировки, ложные срабатывания (VPN, общий
IP, быстрые реконнекты) и деградацию TPS под защитой. Полезные плагины SoulFire для этого:
`server-list-bypass` (обход проверки пинга), `client-settings` (корректный settings-пакет),
`anti-afk` (поведенческий анализ), `chat-logger`/`disconnect-logger` (причины отказов).

## 2. Требование «можно управлять ботами»

### 2.1. SoulFire — четыре уровня управления

| Уровень | Чем | Примеры |
|---|---|---|
| **GUI** | SoulFireClient | инстансы, аккаунты, прокси, плагины, «Overview» со списком ботов, живые статусы |
| **Консоль/CLI** | Команды прямо в панели | `bots start`, `bots stop`, `online`, `bot Bot1,Bot2 say привет`, `instance Test1 repeat 5 move 100 65 200` |
| **Скрипты** | Визуальные графы + durable tasks | триггер «бот вошёл» → `say`, таймеры, условия; исполняет сервер, редактор можно закрыть |
| **Код** | SDK (TS/Python, gRPC-Web) + **MCP** | массовый старт/стоп, потоки статусов, чат, инвентарь, pathfinding, «лизы» контроля над ботом |

Часто используемые команды во время теста:

```
bots start                      # запустить всех настроенных ботов
online                          # кто реально подключён (запрошено ≠ подключено)
bot Bot12 stop-task             # снять текущую задачу
instance Flood say тест         # чат от всего инстанса
move radius 200                 # разойтись по радиусу
collect minecraft:oak_log 64 32 # поведенческая нагрузка
kill-aura (плагин)              # боевая нагрузка
export-basic-render 1280 720    # POV-скриншот для доказательств
say /spawn
stop-task
```

### 2.2. Управление у «заливных» инструментов

- **mc-bots**: консоль в том же процессе — `.list` / `.ls`, `.control <ник>` / `.ctrl`, `.exit <limit>`;
  всё, что без префикса `.`, уходит как чат от всех ботов.
- **BotMark / rust-mc-bot**: только старт/стоп процесса (это осознанный компромисс за производительность).
- **Carpet / BetterStressbots**: команды сервера (`/player <ник> spawn|attack|use`, `/stress count`,
  `/start`, `/stress stop`, `/stress chat /rtp`) — управление мгновенное, но только внутри сервера.

## 3. Требование «максимально лучший стресс-тест»

### 3.1. Подготовка (полчаса, которая экономит сутки)

```
1. Копия сервера на другой порт, бэкап мира и конфигов.
2. Spark на сервер: /spark tps, /spark profiler start|stop, /spark heapsummary, /spark gc
3. server.properties:  max-players=200+, online-mode=false (для окна B),
                       allow-flight=true (если боты летают)
4. bukkit.yml:         connection-throttle: 0      # иначе 1 вход / 4000 мс
5. Оптимизации перед тестом (иначе меряете не то):
   view-distance=8, simulation-distance=4
   paper-world-defaults.yml: spawn-limits (monster 20, creature 5), max-entity-collisions: 2
6. Chunky: /chunky radius 5000 → /chunky start   # предгенерация ДО теста
7. Java: Java 25 + ZGC при 8+ ядрах, иначе Aikar's G1GC
8. Белый список/bypass для машины генератора (см. §1.3, окно B)
```

### 3.2. Пять фаз прогона

| Фаза | Что делаем | Инструмент | Длительность | Что смотрим |
|---|---|---|---|---|
| **1. Baseline** | Пустой сервер | — | 10–15 мин | MSPT < 10 мс, TPS 20.0, CPU, RAM, сеть |
| **2. Ступени** | 10 → 25 → 50 → 100 → 200 ботов, плавный вход | SoulFire (живые боты) | по 10–15 мин на ступень | MSPT (current/median/p95), RAM-тренд, ошибки, дисконнекты |
| **3. Поведение** | ходьба по новым чанкам, копание, чат, инвентарь, команды | SoulFire `<tasks>`, скрипты | 10–15 мин на сценарий | MSPT при генерации чанков, нагрузка на плагины и БД |
| **4. Спайк** | 10 ботов онлайн → +50 за 30 секунд | SoulFire / mc-bots | 3 повтора | просадка ниже TPS 15, время восстановления |
| **5. Выносливость** | 50–75% от целевой ёмкости | SoulFire (живые боты) | **4–8 часов** | рост MSPT, утечки, GC-паузы |
| **(6. Анти-бот)** | flood против включённой капчи | rust-mc-bot/BotMark + SoulFire | 30 мин | блокировки, attack-mode, ложные срабатывания |

### 3.3. Что и чем мерить

| Метрика | Целевое | Где смотреть |
|---|---|---|
| MSPT | < 40 мс (есть запас), 40–50 — предел | `/spark tps`, `/log tps` (Carpet) |
| TPS | 20.0; < 15 — «почти неиграбельно» | там же |
| CPU сервера | < 80% (выше — нет запаса на спайк) | htop / панель, `/spark profiler` |
| CPU/RAM **машины ботов** | не должно быть узким местом | htop на генераторе — иначе меряете его |
| p95 MSPT | сравнить со средним | `/spark tps` |
| Причины киков | появление новых = стоп-условие | консоль + `disconnect-logger` |
| Трафик и TCP | КБ/с и число соединений на бота | панель хостинга / ss |
| Плагины-виновники | > 10% CPU в профиле — разбирать | `/spark profiler` (flamegraph) |

**Стоп-условия (задать до теста):** MSPT > 50 мс, TPS < 20, появляются дисконнекты/ошибки в логе,
RAM сервера у предела, либо CPU генератора > 90%. При срабатывании — фиксируем ступень и
останавливаемся, а не «идём дальше и смотрим, когда упадёт».

### 3.4. Почему нужны все три слоя, а не один

- **SoulFire (10–50 ботов)** даёт *достоверный* ответ: настоящий клиентский код, значит MSPT
  растёт так же, как от реальных игроков. Дороже по железу, зато цифры можно показывать как отчёт.
- **mc-bots / rust-mc-bot (100–1000+)** дают *потолок входа*: где ломается авторизация,
  throttling и анти-бот-слой. Дёшево. Но это синтетика — помечайте в отчёте отдельно.
- **Carpet / BetterStressbots** дают *чистую геймлогику* без сети: плагины, команды, регионы,
  экономика, моб-ИИ. Капча и online-mode вообще не мешают.

Так вы получаете полную картину: «вход держит N соединений; игровую нагрузку держит M живых ботов;
плагины ломаются на K ботах; под защитой флуд блокируется за T секунд».

## 4. Готовый порядок действий под ваши три условия

**Инструменты:** SoulFire (ядро), mc-bots (массовка), rust-mc-bot или BotMark (потолок),
BetterStressbots или Carpet (геймлогика). Опционально mcst (dodoflix) — метрики и web-GUI.

1. **Настроить SoulFire:**
   AI Settings (Base URL, ключ, vision-модель: `llava` локально или Groq vision) →
   плагин **`captcha-solver`**: режим по вашей капче (см. §1.2), Prompt, Response Command, Regex →
   **проверить на одном боте**, что капча реально доходит и решается.
2. **Настроить инстанс под тест:** аккаунты (уникальные ники!), прокси (если нужны),
   `Bots per proxy`, `Proxy check address` = ваш сервер, задержка входа 1–3 с на бота.
3. **Подключить управление:** GUI для наблюдения, командная строка для действий
   (`bots start`, `online`, `bot ... stop-task`), скрипты/SDK для повторяемых сценариев.
4. **Подготовить сервер:** §3.1 (бэкап, Spark, view/sim distance, Chunky, `connection-throttle: 0`).
5. **Фазы 1–5** из §3.2 на SoulFire — это основной, «честный» стресс-тест с капчей.
6. **Отдельным окном** — flood-слой (mc-bots → rust-mc-bot) с bypass для генератора: потолок входа.
7. **Отдельным окном** — анти-бот-тест: капча включена, боты её ломают, смотрим блокировки и TPS.
8. **Собрать отчёт:** MSPT/TPS по ступеням, flamegraph, причины киков, POV-скриншоты, что менять.

## 5. Быстрый чек-лист

**Капча**
- [ ] Определён тип капчи → выбран режим (`MAP_IN_HAND` / `POV_RENDER` / `TEXT_BASED` / `CHAT_MESSAGE`)
- [ ] Vision-модель выбрана и доступна с backend; для map-капчи карта попадает в главную руку
- [ ] Проверено на 1 боте; зафиксировано время решения
- [ ] Для flood-слоя сделан bypass для машины генератора (permission/whitelist/ipset), а не отключение защиты
- [ ] Отдельно проведён анти-бот-тест с включённой защитой

**Управление**
- [ ] `bots start` / `bots stop` / `online` работают, статусы видны
- [ ] Есть скрипт или SDK-программа для повторяемого сценария (экспорт сохранён)
- [ ] Понятно, как снять задачу с одного бота (`bot <ник> stop-task`) и остановить всё разом

**Стресс-тест**
- [ ] Бэкап + отдельный инстанс сервера
- [ ] Spark установлен, baseline < 10 MSPT снят
- [ ] Чанки предгенерированы (Chunky)
- [ ] Ступени с выдержкой 10–15 мин, меняем одну переменную за прогон
- [ ] «Запрошено ≠ подключено»: сверяем `online` с числом запущенных
- [ ] Стоп-условия и наблюдатель назначены
- [ ] После теста: явная остановка ботов, наблюдение восстановления, откат окружения
- [ ] Отчёт: MSPT/TPS, p95, flamegraph, причины киков, что починить
