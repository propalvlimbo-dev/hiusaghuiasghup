# SoulFire: тест своего сервера, капча и прокси

Практическое руководство. Всё описывается для **вашего собственного сервера** — это и есть
заявленный сценарий SoulFire. На чужих серверах без разрешения владельца запускать ботов нельзя.

---

## Часть 0. Что подготовить заранее

1. **SoulFire Server (backend)** — там живут боты. Где запускать:
   - **Лучше всего:** отдельная машина/VPS, отличная от машины с Minecraft-сервером. Иначе боты и цель
     конкурируют за CPU/RAM, и вы измеряете не сервер, а самих себя.
   - Варианты запуска: `SoulFireDedicated-x.y.z.jar` (Java 21+/25+), Docker-образ из репозитория
     (`Dockerfile`), шаблон для панели Pterodactyl (`soulfire_egg.json`), либо GUI-клиент SoulFireClient
     в локальном режиме (он поднимет backend сам, но для флотов не подходит).
   - Скачать: https://github.com/soulfiremc-com/SoulFire/releases (для GUI — релизы SoulFireClient).
2. **Клиент** — GUI (SoulFireClient) для ручной работы или CLI/SDK для автоматизации.
3. **Инстанс (instance)** — создайте **отдельный инстанс под тест**. Инстанс — это граница настроек и прав:
   свои аккаунты, прокси, плагины, скрипты, лимит ботов.
4. **Аккаунты** — offline (для оффлайн-режима) или Microsoft. Для тестов лучше **отдельные тестовые
   аккаунты**, а не свои боевые. Имена у каждого бота должны быть разными: дубликат = кик предыдущего.
5. **Совпадение версий** — в Bot Settings выберите протокол, соответствующий вашему серверу
   (SoulFire умеет всё: от Classic/Alpha/Beta и Bedrock до свежих версий через ViaFabricPlus). ViaVersion
   на вашем сервере при этом не нужен.
6. **Одно живое подключение до теста** — сначала зайдите на свой сервер нормальным клиентом, потом одним
   ботом SoulFire. Если бот не пускается (вайтлист, онлайн-режим, анти-чит), устраните это **до** нагрузки.

## Часть 1. Как протестировать свой Minecraft-сервер

### 1.1. Сформулируйте вопрос и предел (5 минут, экономит дни)

Один вопрос, один измеримый критерий. Примеры:

- «Держит ли сервер 50 входов с реалистичными задержками без роста tick time выше N мс?»
- «Переживает ли лобби-плагин массовые реконнекты?»
- «Не лагает ли генерация чанков, когда 20 ботов ходят по новым территориям?»

Определите **стоп-условие** заранее (tick duration, % неудачных логинов, насыщение backend) и того, кто
останавливает прогон.

### 1.2. Запишите манифест прогона

Шаблон из документации SoulFire (заполняйте до запуска, иначе результаты не сравнимы):

```
Run name:
Start time and timezone:
Question and pass criteria:
Minecraft software/version:
Minecraft plugins and proxy topology:
SoulFire server/client version:
SDK version or script export, if used:
Target address from the SoulFire backend:
Accounts and authentication type:
Proxy routes:
Bot count at each stage:
Join delay and observation duration:
Bot behavior:
Stop condition:
Baseline metrics:
Result and artifact locations:
```

### 1.3. Подготовьте цель

- Сделайте **резервную копию мира и конфигов** — тест может что-то сломать или изменить.
- Запишите: софт (Paper/Purpur/Fabric…), версию, плагины, топологию прокси, режим авторизации.
- Отключите на тестовом окружении всё, что мешает измерению: анти-бот, капчу, rate-limit по IP,
  агрессивный анти-чит, а также лишние плагины. **Для тестовой копии сервера это самый простой путь.**
- Проверьте: лимит игроков, вайтлист, бан-листы, права, требования авторизации.
- По возможности используйте **disposable-копию мира** для копания/строительства.

### 1.4. Замер базовой линии

Наблюдайте сервер **без ботов**: tick duration (TPS/MSPT), CPU, RAM, число игроков, фоновая активность.
Зафиксируйте те же метрики на стороне SoulFire backend. Синхронизируйте часы на обеих машинах —
иначе логи не сопоставить. Удобно профилировать через **Spark** (`spark <command>` есть прямо в консоли SoulFire,
и плагин Spark на Minecraft-сервере).

### 1.5. Ступенчатая нагрузка (главное правило: не смешивайте «запрошено» и «подключено»)

| Шаг | Действие | Что записать |
|---|---|---|
| 1 | Без ботов | baseline: MSPT/TPS, CPU, RAM |
| 2 | **1 бот** | время до рабочего состояния, состояние мира, дисконнекты |
| 3 | **5 ботов** | фактическое число онлайн, ошибки логина |
| 4 | **10 ботов** | то же + MSPT |
| 5 | **20 ботов** | то же |
| 6 | Сверка со стоп-условием | стоп, если MSPT/дисконнекты/backend «упёрлись» |

- Задержка входа (`join delay`) должна быть реалистичной — резкий «залп» входов измеряет другое, чем
  плавный рейт.
- На каждой ступени выдерживайте заданное время наблюдения и **повторяйте** ступень, если нужно отличить
  всплеск от устойчивого поведения (записывайте повтор отдельно).
- Смотрите в Overview SoulFire и в консоль Minecraft одновременно.
- Меняйте **по одной переменной** за эксперимент: число ботов, задержка, поведение, маршрут прокси,
  настройки сервера.

### 1.6. Поведенческие сценарии (иначе тест нерепрезентативен)

Idle-боты не отражают реальную игру. Прогоняйте:

- **Чат и команды:** `say <message>` (в т.ч. команды сервера), сценарные сообщения.
- **Движение и чанки:** pathfinding и команды `move x y z`, `move radius <r>`, `follow <entity> <r>`,
  `mimic <entity>`. Разделяйте ходьбу по уже загруженным чанкам и генерацию новых — это разная нагрузка.
  Для сравнимых прогонов повторяйте **одни и те же координаты**, не случайный маршрут.
- **Инвентарь и мир:** `inventory ...`, `collect <block> <amount> <radius>`, `excavate rectangle ...`,
  `excavate sphere ...`, `build`-задачи, сундуки/крафт/печки/торговля с жителями.
- **Авторизация и реконнекты:** по одному пути за раз — offline-аккаунт, Microsoft, плагин авторизации.
  Запишите причину кика и время до восстановления.
- **Комбат:** `kill-aura` с настройками дальности/кулдауна/защищённых игроков, если тестируете боевую часть.

Готовые команды для быстрых проверок:

```
say Привет, это нагрузочный тест
move 100 65 200
collect minecraft:oak_log 64 32
excavate sphere 100 60 200 8
bot Bot1,Bot2 say тест
instance Test1 repeat 10 say ping
```

Плюс `control forward|backward|left|right|jump|sneak|reset`, `lookat`, `useitem`, `click left|right`,
`interact <entity> <hand>`, `stop-task`, `online`, `health`, `respawn`.

### 1.7. Массовый вход и масштаб

- Плавный вход: настраиваемый `join delay` + задержка между ботами в инстансе.
- Массовый старт/стоп: команды `bots start` / `bots stop` для выбранных инстансов, либо SDK
  (`Starting, stopping, and restarting one bot, explicit bot IDs, or a count`).
- Для больших прогонов автоматизируйте воспроизведение через **визуальный скрипт** в GUI,
  **durable tasks** или **SDK** (TS/Python поверх gRPC-Web) — руками по 100 ботов управлять не выйдет.

### 1.8. Сбор доказательств и завершение

- **POV-скриншот глазами бота:** `export-basic-render [width height]`, `export-render-debug-dump [w h] [max_distance]`.
- Экспорт карт: `export-map [map_id]`.
- Логи: плагины `chat-logger` и `disconnect-logger` — чат и причины отключений в терминал без спама дублями.
- Метрики: MSPT/TPS/CPU/RAM цели **и** backend раздельно (если перегружен backend — измерения недействительны).
- В конце: остановите автоматизацию и ботов **явно**, убедитесь, что онлайн вернулся к базовому,
  реконнекты прекратились, и наблюдайте восстановление столько же, сколько длилась ступень нагрузки.
- Верните тестовое окружение в исходное состояние (мир из бэкапа, плагины как были).

### 1.9. Полезное для «своего сервера»

- **Онлайн-режим мешает оффлайн-ботам.** Если ваш публичный сервер работает в online-mode, а тестировать
  хотите оффлайн-ботами, есть официальный путь: прокси-плагин **SoulFireBypass**
  (https://github.com/soulfiremc-com/SoulFireBypass, https://modrinth.com/plugin/soulfirebypass) +
  встроенный плагин `forwarding-bypass` в режиме `SF_BYPASS` с общим секретом. Тогда обычные игроки
  логинятся как раньше, а боты с валидным ключом идут оффлайн-путём.
  Это узкая «дверь» для тестов, **ключ = пароль**: никому не показывайте и ротируйте при утечке.
- Также `forwarding-bypass` умеет `LEGACY`, `BUNGEE_GUARD` и `MODERN` (Velocity) — если тестируете
  сеть за BungeeCord/Velocity.
- **AuthMe-подобная авторизация** в чате: плагин `auto-register` ловит в чате `/register`, `/reg`,
  `/login`, `/l` и отправляет заданный шаблон команды (по умолчанию `/register %password% %password%`)
  через случайную задержку. Используйте **отдельный тестовый пароль**, он виден всем, у кого есть доступ
  к настройкам инстанса.
- **`auto-reconnect`** полезен при тестах устойчивости, но он же искажает картину «сколько ботов отвалилось».
  Для чистых измерений логинов его лучше выключить и включить отдельно на этапе проверки восстановления.

## Часть 2. Если на сервере капча

Сначала — самое важное:

> **Если у вас есть доступ к серверу, самый простой способ — не решать капчу, а исключить её в тестовом
> окружении.** Капча/анти-бот нужны для защиты от чужих ботов, а не от вашего собственного нагрузочного
> теста. На тестовом инстансе сервера отключите плагин капчи, добавьте IP backend-машины в вайтлист,
> либо поставьте отдельную защиту с ключом.

### 2.1. Если капчу всё-таки нужно проходить (или вы тестируете саму капчу)

В SoulFire есть встроенный плагин **`captcha-solver`** (в списке как `ai-captcha-solver`,
«Solve captcha images using AI»). Он работает через общий **AI Settings** и LLM.

**Сначала настройте AI-провайдера** (AI Settings в нужном инстансе):

| Настройка | Значение |
|---|---|
| API Base URL | для OpenAI — по умолчанию; для Groq — `https://api.groq.com/openai/v1`; для Ollama — адрес вашего локального сервера |
| API Key | ключ провайдера |
| API Request Timeout / Max Retries | по умолчанию 60 с и 5 попыток; слишком большие значения только замедлят реакцию на отказ |
| Модель | задаётся **отдельно для каждой AI-функции**, а не одной на всё |

Провайдер должен быть доступен **с машины, где крутится SoulFire backend** (внутри Docker — с учётом сети контейнера).

**Затем настройте сам плагин.** Два принципиально разных режима:

| Режим | Когда использовать | Ключевые настройки |
|---|---|---|
| `TEXT_BASED` | Текст капчи **уже есть в чате**, его надо только извлечь | **Captcha Regex** с группой захвата (по умолчанию `/captcha (\w+)`) + Response Command |
| `CHAT_MESSAGE` | Сообщение в чате **запускает** распознавание картинки | **Text Trigger** (текст-триггер) + Prompt + Model + Image Source |

Источник изображения (**Image Source**):

| Источник | Что это за капча |
|---|---|
| `MAP_IN_HAND` | Капча отрисована на **карте в руке** бота (частый приём на анти-бот плагинах) |
| `POV_RENDER` | Капча висит в мире/на экране, и её надо «увидеть» глазами бота (рендер без окна, Vulkan) |

Прочие настройки: **Prompt** (системная инструкция модели), **Model**, **Response Command**
(шаблон ответа, куда подставляется распознанный текст), **POV Render Width/Height** (разрешение
POV-снимка под `POV_RENDER`).

**Модель обязательно должна уметь работу с изображениями**, если используете картинку:
- OpenAI — vision-модель;
- Groq — например `meta-llama/llama-4-scout-17b-16e-instruct` (не оставляйте текстовую `gpt-oss`!);
- Ollama локально — по умолчанию в плагине заложена `llava` (локальный вариант = капча не уходит в облако).

**Порядок проверки (только так, не иначе):**

1. Сначала один бот на тестовом сервере, ноль прокси, ноль лишних плагинов.
2. Убедитесь, что капча вообще **доходит до бота** — проверьте текст в чате или изображение
   ([bot view inspection](https://soulfiremc.com/docs/how-to/pov)]; «модель не спасёт отсутствующую карту
   или нерабочий кадр».
3. Если триггер не срабатывает — проверьте: плагин включён, триггерный текст/регулярка совпадают с
   реальным сообщением сервера, ответная команда соответствует ожидаемому формату.
4. Если модель отвечает мусором — правьте Prompt, проверяйте кроп/разрешение POV, ставьте vision-модель.
5. Работает на одном боте → увеличивайте количество.

**Ограничения из кода плагина (важно для ожиданий):**
- ответ модели обрезается до ~32 символов, лимит генерации 64 токена — для длинных кодов/фраз не подойдёт;
- перед отправкой текст проходит очистку под чат;
- если картинка из `POV_RENDER` не читается на этом разрешении, никакая модель не поможет — поднимите
  `POV Render Width/Height`;
- для `MAP_IN_HAND` в руке бота действительно должна быть та самая карта.

**Диагностика по симптому:**

| Симптом | Что проверить |
|---|---|
| Ошибка авторизации | ключ, доступ проекта, доступность модели |
| Model not found | точный ID модели у этого провайдера |
| Timeout / connection error | сетевой маршрут, base URL, статус провайдера |
| Запросов нет вообще | плагин включён? триггер совпадает? скрипт исполняется? |
| Слишком много запросов | частота триггера, циклы, реконнекты, лимиты |
| Мусорный ответ | Prompt, входное изображение, лимиты вывода, возможности модели |

**Юридически/этически:** `captcha-solver` — инструмент для тестирования **своего** сервера и своих
анти-бот-сценариев. Применение на чужом сервере идёт против правил сервиса и предупреждения в README.

### 2.2. Стенд «проверить свою капчу ботами» (быстрый цикл)

Задача: не «пройти капчу», а **понять, что именно ваша защита не ломает ботов**, и подкрутить её.
Для этого нужен вход за доли секунды, картинка капчи на диске и лог каждого шага.

**Инструмент: `scripts/captcha-test-bot.js`** (Node.js, одна зависимость `mineflayer`).

```bash
npm init -y && npm i mineflayer

# один бот, ручной режим: увидел карту-капчу → сохранил PNG → ждёт ваш ввод кода
node captcha-test-bot.js --host play.example.com --port 25565

# флот из 5 ботов, авто-регистрация и авто-логин по вашему паролю
node captcha-test-bot.js --host play.example.com --count 5 --password "pass123"

# авто-ответ через OCR (капча без сильных помех): npm i tesseract.js
node captcha-test-bot.js --host play.example.com --answer-mode ocr --ocr-langs eng

# ответ уходит командой, а не чатом
node captcha-test-bot.js --host play.example.com --captcha-command "/captcha "
```

Что делает:

| Шаг | Результат |
|---|---|
| вход | 0,1–0,5 с (протокольный бот, без рендера) |
| текст в чате | авто `/register {pass} {pass}` и `/login {pass}` (шаблоны меняются флагами) |
| текстовая капча | regex ловит код из чата и отвечает (как чат или как команда) |
| **карта-капча** | декодирует пакет карты и пишет `captcha-images/<бот>_map_XXXXXX.png` (128×128) |
| ручной режим | печатает путь к PNG и спрашивает код; вы смотрите — бот отвечает |
| **OCR-режим** | tesseract.js читает код с картинки и отвечает сам |
| лог | `captcha-test.log`: чат, кики, ответы, ошибки — доказательства для правки защиты |

Установка проверена: PNG-кодек (палитра карт 1.16+, работает и на 1.21.x) прогнан через независимый
парсер — все CRC чанков валидны, картинка 128×128 RGBA открывается любым просмотрщиком.

**Инструмент 2: `scripts/stress-bots.js` — нагрузка + капча + регистрация в одном.**

Полный набор «бот для стресс-теста с обходом капчи и настоящим появлением»:

```bash
npm i mineflayer                     # обязательно
npm i socks minecraft-protocol       # если нужны прокси
npm i tesseract.js                   # если нужен авто-OCR капчи-картинки

node stress-bots.js --host play.example.com --count 50 --password "pass12345"
node stress-bots.js --host play.example.com --count 50 --password pass --proxy-file proxies.txt
node stress-bots.js --host play.example.com --count 100 --move --chat-every 90 --stats-every 10
node stress-bots.js --host play.example.com --count 3 --captcha manual      # ручная разгадка

# эмуляция атакующего с платным распознаванием капчи (RuCaptcha/2Captcha):
node stress-bots.js --host play.example.com --count 20 --captcha service \
  --solver rucaptcha --solver-key ВАШ_КЛЮЧ
```

| Что делает | Как |
|---|---|
| вход | 0,1–0,5 с на бота, `--join-delay` регулирует частоту |
| регистрация / логин | авто по шаблонам `--register-cmd "/register {pass} {pass}"`, `--login-cmd "/login {pass}"` |
| текстовая капча | regex из чата → ответ (чатом или командой `--answer-cmd "/captcha "`) |
| **капча-картинка** | PNG сохраняется в `captcha-images/`, затем `--captcha ocr` (tesseract.js), `--captcha manual` или `--captcha service` (платный API RuCaptcha/2Captcha — эмуляция «платформенного» бота) |
| **настоящее появление и нагрузка** | боты ходят (`--move`), прыгают, спринтуют, крутят головой, машут рукой, пишут в чат (`--chat-every`) — грузят чанки, физику и пакеты |
| прокси | `--proxy-file proxies.txt` → каждому боту свой SOCKS5 (проверено: клиент mineflayer принимает свой сокет) |
| статистика | каждые `--stats-every` секунд: онлайн, спавны, капчи, кики, средний вход |
| лог | `stress-bots.log` — чат, кики, ответы (доказательства для отчёта) |

Авто-капча работает не всегда: у шумной карты OCR ошибается. Тогда PNG остаётся на диске,
в логе видно «OCR не распознал», и можно либо поднять ручной режим на 1–5 ботах, либо ослабить шум —
именно в этом и смысл стенда: как править защиту.

**Другие готовые решения того же класса** (если нужен не стенд, а «решатель»):

| Инструмент | Что даёт |
|---|---|
| **SoulFire `captcha-solver`** | единственный, кто решает капчу **через AI-vision** и умеет POV; медленный вход — цена |
| `mineflayer-item-map-downloader` | та же выгрузка карт в PNG для mineflayer (нужен `sharp` — нативный модуль) |
| `FlayerCaptcha` (MIT, 2025) | модуль mineflayer: события `imageReady` / `frameInfo` с готовыми PNG карты |
| `mineflayer-install-captcha` | npm-обёртка: авто-обработка и сохранение карт капчи |
| `recaptchaUser/minecraft-captcha-solver` | Python-скрипт: простое чтение капчи (OCR) |

### 2.3. Чек-лист усиления капчи (что править после прогона стенда)

Прогоните стенд на своей капче. Если бот отвечает — усильте защиту по этому списку
(параметры — из конфигов распространённых плагинов: `mapcha`, `Minecaptcha`, `Captcha`):

| Рычаг | Слабое значение | Сильное значение | Против кого работает |
|---|---|---|---|
| Шум на картинке | обводка (`lines`, `points`) = `false` | `points: true`, `lines: true`, больше линий/точек | против простого OCR |
| Инверсия | `invert_color: false` | периодически `true` | ломает обученный на «чёрное на белом» OCR |
| Длина кода | 3–4 символа, только цифры | 6+ символов, цифры+буквы разного регистра | против перебора |
| Число попыток | `tries: 3` | `tries: 1` | против подбора по ответам |
| Лимит времени | `time: 600` | `time: 20–30` | против медленного OCR в цикле |
| Движение до ответа | нет | `require-move-action: true` | против ботов, которые только читают чат |
| Заморозка/слепота | нет | `freeze_player`, `blind_player`, `hide_players` | мешает автоматизации «по состоянию мира» |
| Кеш решения | `cache: false` | `cache: true` | один раз пройденная капча не прощается второй раз |
| Регулярная смена картинки | одна карта на всех | новая карта каждому + ротация | убивает заготовленные ответы |

Что **не поможет**: усложнять формулировку в чате (regex ловит что угодно), менять плагин на другой
такой же. Помогает сочетание «шумная картинка + 1 попытка + 20 секунд + лимиты по IP».

Отдельно про лимиты: капча защищает от флудеров (`rust-mc-bot`, `mc-bots`), потому что те **не рендерят
карту и не умеют OCR** — для них она стена. А вот от вашего стенда и от SoulFire с vision-AI карта
защищает только своей шумностью — её и наращивайте.

> ⚠️ Стенд запускайте только против своего сервера или с письменного разрешения владельца.

### 2.4. Коммерческие «бот-платформы» (NeoProxy, BareAPI, BebraProxy, BareClient): что за ними

Публичных сайтов, GitHub-репозиториев и документации у них нет — это **закрытые серые платформы
«загона ботов»**, которые продают в Telegram/Discord. Публично они упоминаются только в обсуждениях
владельцев серверов — как источник бот-атак. Проверить состав и безопасность такого бинарника
невозможно: исходников нет, оплата криптой анонимам.

Что они делают по существу — ничего магического:

| Слой | Техника | Что важно |
|---|---|---|
| Вход | протокольные боты (не клиенты) | то же, что `scripts/stress-bots.js`, только закрытое |
| IP | пулы резидентских/мобильных прокси | арендуются на месяц за деньги |
| Капча-картинка | читают **пакет карты напрямую** и распознают (свой ML или сервис) | сервер отдаёт боту все 16 384 байта карты — рисовать «сложную картинку» бесполезно само по себе |
| Капча-текст | regex/парсинг чата | ломается тривиально |
| Капча-задание | распознавание меню/структур + база ответов | здесь их и ловят кастомные задания |
| Поведение | скрипты движения/чата | пакетная проверка и rate-limit их режут |

**Что удалось найти по каждому (проверка на 04.10.2026):**

| Платформа | Публичный код | Что известно |
|---|---|---|
| **BebraProxy** | ✅ исходники есть в открытом доступе | Java, пакет `ru.justnanix.bebraproxy`; на GitHub лежит форк `Anyachkaa/BebraProxy` (320 файлов, 1.12–1.20), в закрытых форумах — раздача «BebraProxy (исходники) — ядро для DDOS-бот-атак» (автор m1x_native, теги justnanix). Описание в README команды: *«Нагружает сервер путём массового отправления нестандартных пакетов ботами»* (сейчас заглушка «в разработке») |
| **NeoProxy** | ❌ не найден | Единственное публичное подтверждение существования — плагин `Rushcik/NeoProxyBlocker`, который банит ники с префиксами `NeoProxy_` / `Neo_`. Исходников нет: ни на GitHub, ни в поиске |
| **BareAPI / BareClient** | ❌ не найден | Ни репозиториев, ни сайта, ни документации. Упоминания только в тредах владельцев серверов |

**Что внутри BebraProxy (по коду):** это не «клиент», а **прокси-сервер**: игрок подключается к нему
обычным клиентом и через него запускает ботов на цель. Внутри — своя реализация клиентского протокола
(handshake, login, chat, position, inventory, chunks), `ProxyManager` с двумя пулами прокси (для ботов
отдельно, для входа самого игрока отдельно), `PlanManager`/`PlanAccount` — платные подписки по ключам
со сроком и привязкой к стране/IP, `MirrorRecord`/`CommandMirror` — боты повторяют движения владельца
(«ходят за школьником»), `MacroRecord` — записанные маршруты, `Bot.captchaTries = 3` — попытки капчи.
То есть архитектурно это ровно то же, что делает `stress-bots.js`, + биллинг и пакетные крашеры.

**Почему не стоит брать это даже для своего сервера:** версии протокола 1.12–1.20 (не 1.21.x), код
2023–2024 годов без поддержки; в «слитых» сборках такого класса обычны бэкдоры и кража аккаунтов;
это инструмент атаки, а не измерений (нет статистики, метрик, плана нагрузки). Для своего сервера
`stress-bots.js` даёт те же возможности без этих рисков, а «крашеры» тестируют не нагрузку, а
устойчивость к эксплойтам — это отдельная задача и с чужими бинарниками её лучше не делать.

**Ключевой факт для защиты:** капча-карта — не барьер для протокольного бота. Мы это уже доказали
собственным кодеком: `scripts/stress-bots.js` принимает пакет карты и сохраняет PNG 128×128
**без клиента и рендера**. Значит защита строится не на «сложной картинке», а на: лимитах по IP/подсети,
проверке поведения (падение, инвентарь, ClientSettings/бренд, странные пакеты), одной попытке,
коротком таймере и кастомных заданиях, к которым боты не обучены.

**Как воспроизвести «лучшего бота» на своём сервере:** `stress-bots.js` + платный API распознавания
капчи (RuCaptcha/2Captcha и аналоги: отправляете PNG — получаете код) вместо OCR. Это то же самое,
что делают платформы внутри, но с логами, контролем и без чужого бинарника.

> ⚠️ Такие платформы против чужого сервера — это не «тест», а атака (ст. 272 УК РФ и смежные).
> Против своего сервера они не дают ничего сверх открытых инструментов.

## Часть 3. Где взять прокси для ботов

### 3.1. Нужны ли они вообще

На **своём** сервере прокси часто **не нужны**: чем меньше «прослоек», тем чище измерения (не путайте
лимиты сервера с лимитами прокси). Прокси нужны, когда:

- сервер/прокси-слой ограничивает число подключений или рейт **с одного IP**;
- у вас анти-бот по IP (например, EpicGuard) и вы хотите проверить, как он отработает на «разных» игроках;
- нужно смоделировать реальное распределение игроков по сетям/странам;
- **нельзя светить IP backend-машины**, и вы хотите отвязать свои тестовые прогоны от него;
- нужен «разлогин» бота под другим адресом после бана/рейт-лимита.

### 3.3. Бесплатные прокси и свой вариант

- **Бесплатные публичные прокси не рекомендуются**: они ненадёжны, часто уже в бан-листах у анти-ботов,
  а трафик может читаться владельцем. README SoulFire прямо предупреждает об этом.
- **Свой прокси на своём VPS** — рабочий вариант для теста своего сервера и для полного контроля:
  поднять SOCKS5/HTTP (danted, 3proxy, squid) на паре мелких VPS и импортировать их. Дёшево, стабильно,
  IP «чистые» (никто их до вас не пачкал). Для распределения по странам — VPS в разных локациях.
- **Мобильные/резидентные** нужны, если анти-бот серьёзно фильтрует datacenter-диапазоны.

### 3.4. Как импортировать и настроить

**GUI:** инстанс → **Proxy Settings** → выбрать тип → вставить/импортировать **по одному прокси на строку** →
сохранить → прогнать **проверку прокси** до подключения ботов.

**CLI:** `--proxy-file <файл>` (+ `--proxy-type` для однотипного файла; для смешанного URI-формата тип не указывать).

**Поддерживаемые типы:** HTTP, SOCKS4, SOCKS5, URI. **`https://` не поддерживается.**

Форматы (сокращённо):

```
ip:port                                   # без авторизации
ip:port:username:password                 # логин+пароль
username:password@ip:port                 # альтернативная запись

socks5://ip:port
socks5://username:password@ip:port
socks4://username@ip:port                 # SOCKS4 без паролей
http://username:password@ip:port
```
Смешанный список — только через URI-записи (`socks5://...`, `http://...`) в одном файле.

**Настройки, которые реально влияют на тест:**

| Настройка | По умолчанию | Зачем менять |
|---|---|---|
| **Bots per proxy** | `-1` (без лимита, но распределяет равномерно) | поставьте лимит (напр. `10`), чтобы проверить работу очереди и реалистичный рейт с IP; боты без свободного прокси ждут в очереди |
| **Shuffle proxies** | `false` | включите, чтобы не привязывать первые боты всегда к первым прокси |
| **Proxy check address** | `mc.hypixel.net` | ❗**смените на адрес своего сервера** — иначе проверяете прокси не туда, куда подключаетесь |
| **Proxy check concurrency** | `10` | сколько проверок параллельно |
| **Proxy check timeout** | `30` сек | увеличьте для медленных/далёких прокси |
| **Use proxies for account auth** | — | трафик Microsoft-авторизации маршрутизируется **отдельно** от игрового; если прокси блокирует auth — отключите для проверки |

Ключевой практический факт из документации: **игровой трафик бота и трафик авторизации Microsoft могут идти
разными маршрутами** — это частая причина «прокси рабочие, а логин падает».

### 3.5. Порядок проверки прокси (не пропускайте)

1. Подключите **одного** бота **напрямую** — базовая линия.
2. Импортируйте **один** прокси и проверьте его.
3. Подключите того же бота через этот прокси.
4. Сравните логи сервера и фактический source address (в логах своего сервера видно, какой IP пришёл).
5. Только потом — весь список и боты.

## Часть 4. Итоговый чек-лист

**Тест своего сервера**
- [ ] backend на отдельной машине; бэкап мира и конфигов
- [ ] отдельный инстанс под тест; отдельные тестовые аккаунты и уникальные ники
- [ ] выбран правильный протокол/версия; один ручной вход + один бот проверен заранее
- [ ] записан манифест прогона и стоп-условие
- [ ] baseline без ботов; ступени 1 → 5 → 10 → 20 → …
- [ ] поведенческие сценарии (чат, движение/чанки, инвентарь, реконнект, комбат)
- [ ] метрики обеих машин сняты раздельно; часы синхронизированы
- [ ] доказательства: POV-рендер, экспорт карт, логи чата/дисконнектов
- [ ] явная остановка, наблюдение восстановления, откат окружения

**Капча**
- [ ] сначала рассмотреть исключение: тестовый инстанс без капчи / вайтлист IP / ключ-байпас
- [ ] если решать: настроены AI Settings, выбрана **vision**-модель, режим (TEXT_BASED vs CHAT_MESSAGE) и
      источник изображения (MAP_IN_HAND vs POV_RENDER) совпадают с реальной капчей сервера
- [ ] проверено, что капча доходит до бота (текст/карта/POV), ответ ≤ 32 символов
- [ ] проверено на одном боте, затем масштабирование

**Прокси**
- [ ] решено, нужны ли они вообще (на своём сервере часто нет)
- [ ] источник — каталог https://soulfiremc.com/get-proxies или свои VPS-прокси; бесплатные — нет
- [ ] тип HTTP/SOCKS4/SOCKS5/URI (без `https://`), формат списка соблюдён
- [ ] `Proxy check address` = ваш сервер; лимит `Bots per proxy` задан осознанно; shuffle включён
- [ ] проверено: 1 бот напрямую → 1 прокси → затем все
